# Phase 5 Testing & Hardening

Phase 5 adds regression tests and small hardening changes around the Phase 3 commerce flow, Phase 4 analytics, admin authentication, downloads, responsive behavior, and accessibility. It does not add a database migration.

## Automated checks

Run these from the project root after `npm install` or `npm ci`:

```bash
npm run test:security
npm run typecheck
npm run lint
npm run build
```

For a production-equivalent verification with all required environment variables loaded:

```bash
npm run verify:production
```

`verify:production` runs the security/accessibility contract tests, TypeScript, ESLint, environment validation, and the production Next.js build.

## What the regression tests cover

- Every protected `/api/admin/*` route invokes the shared `isAdminAuthenticated()` guard.
- Admin session tokens reject expired, tampered, and wrongly signed values.
- Admin cookies retain `HttpOnly`, `SameSite=Strict`, and production-only `Secure` behavior.
- Paystack webhook signatures are verified against the exact raw request body using SHA-512 HMAC.
- The payment webhook verifies signature before database access and checks order amount/currency.
- Paid downloads require a paid order and an unexpired download timestamp.
- Download tokens must be UUID v4 values generated by the application.
- Public resource query allow-lists and pages do not expose `file_url`.
- The Phase 3 database migration keeps `file_url` outside anon/authenticated column grants.
- Admin editor modals expose dialog semantics, trap keyboard focus, close with Escape, and restore focus.
- Core Phase 3/4 pages retain mobile-first layout contracts.
- Checkout fields retain programmatic labels and accessible error announcements.

## Manual production QA

### Admin authentication

1. Visit `/admin` while signed out and confirm protected data is not available.
2. Enter an incorrect admin password and confirm login is rejected.
3. Sign in with the correct password and confirm Content, Resources, Services, Leads, Orders, and Analytics load.
4. Sign out and confirm the admin session is cleared.

### Paid checkout

1. Create or use a published paid resource with a valid HTTPS `file_url`.
2. Open `/resources/<slug>` and submit customer name and email.
3. Confirm checkout redirects to Paystack.
4. Complete a test payment.
5. Confirm the order remains pending until the signed webhook is processed.
6. Confirm the webhook marks the order `paid` and creates a 48-hour download token.
7. Confirm `/order/<token>` shows the product title and download button.
8. Confirm `/api/download/<token>` serves the file without exposing the stored `file_url` in the browser address bar.
9. Confirm the resource download count increments after a successful download.

### Invalid and expired downloads

1. Change one test order's `download_expires_at` to a past timestamp and confirm its download returns HTTP 403.
2. Try `/api/download/not-a-token` and confirm it returns HTTP 404.
3. Try a valid-format UUID that does not exist and confirm it returns HTTP 404.
4. Confirm a pending/failed order cannot download even if a token is manually present.

### Webhook hardening

1. Send a webhook request without `x-paystack-signature` and confirm HTTP 401.
2. Send the same body with an invalid signature and confirm HTTP 401.
3. Confirm a valid signed `charge.success` event with a mismatched amount or currency does not mark the order paid.
4. Re-send an already processed valid webhook and confirm it remains idempotent.

### `file_url` privacy

1. Inspect `/resources`, `/resources/<slug>`, checkout responses, and order confirmation HTML/network responses.
2. Confirm no response contains the stored resource `file_url`.
3. Using the Supabase anon key, attempt to select `file_url` directly from `resources`; the database should reject access to that column.

### Responsive checks

Check these routes at 320 px, 375 px, 768 px, 1024 px, and desktop widths:

- `/resources`
- `/resources/<slug>`
- `/order/<token>`
- `/order/complete`
- `/admin`, especially Orders and Analytics

Confirm there is no page-level horizontal overflow, buttons remain usable, checkout fields fit the viewport, and the admin section navigation can scroll horizontally on narrow screens.

### Accessibility checks

1. Navigate the entire checkout form using only Tab/Shift+Tab.
2. Open each admin editor modal using the keyboard.
3. Confirm focus moves into the modal, remains trapped inside it, and Escape closes it.
4. Confirm focus returns to the control that opened the modal.
5. Confirm visible focus rings appear on links, buttons, fields, selects, and textareas.
6. Confirm form errors are announced through `role="alert"`.
